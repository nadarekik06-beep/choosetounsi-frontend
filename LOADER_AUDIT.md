# Loader coverage audit — storefront + seller dashboard

Every loading state in this app goes through `<BrandLoader />` (`components/brand/`).
The tables below are generated by a scan of `app/`, `components/`, `hooks/` and `context/`;
this header is the summary and the list of deliberate exceptions.

## Coverage

| | Before | After |
|---|---|---|
| Routes with their own `loading.tsx` | 7 / 57 | 56 / 57 (only the dev-only `/dev/loader-preview` has none) |
| Client components fetching on mount, wired to BrandLoader | 34 / 96 | 63 / 96 — the other 33 are widgets, listed below |
| Files with async actions, pending state shown with the inline loader | 26 / 46 | 43 / 46 — the other 3 are not UI states, listed below |
| Leftover generic loaders (Loader2, CSS spinners, text-only "Loading…") | 9 found by grep + ~20 hand-made CSS spinners | 0 |

## How loading works now

- **Navigation** — `NavigationLoaderProvider` (root layout) shows one BrandLoader overlay as soon as a route
  change starts: link clicks (capture phase; buttons nested in a link are ignored), `router.push` /
  `router.replace` (the app router instance is wrapped), back / forward (`popstate`). A change of search params
  on the same page is an in-page refresh, not a navigation.
- **Hard page loads** — the overlay is in the server HTML (behind the usual 150ms delay) and stays until the
  page has registered its first fetch.
- **First load of a page** — `usePageLoading(loading)` keeps the overlay up until that page's first fetch is
  done, then it fades out (min 300ms once shown). It only holds the *first* load; later refetches are in-page.
  An optional label is shown under the mark (image search: "Analyzing your image…", forecast: "Calculating
  your forecast…").
- **`loading.tsx`** — every segment renders `<RouteLoading />`, which holds the same overlay instead of drawing
  a second one (no stacking, and the overlay can fade out, which a Suspense fallback cannot).
- **Seller dashboard** — `SellerShell` mounts an `area` overlay over its content (sidebar + topbar stay visible);
  the fullscreen one steps aside while it is mounted. `AuthGuard` holds the overlay while the session is checked.
- **Never stuck** — the overlay gives up after 15s (the page shows its own error state); a navigation that
  produces no route change in 8s is treated as a false start.
- **No double loaders** — while the overlay is up, section/fullscreen BrandLoaders inside the page hide
  themselves (keeping their space) and managed ones don't start, so none flashes as the overlay fades.
- **In-page refreshes** (pagination, filters, search typing, tab switch) — `RefreshCover` / `LoadingCover`: a
  section loader over that block only, old content dimmed underneath.
- **Buttons** — `BusyLabel`: the label stays in place but hidden (button keeps its width) with the inline
  loader over it; button disabled while busy.
- **i18n** — `loader.*` keys in EN / FR / AR (loading, tagline, aiTyping, analyzingImage, forecasting,
  optimizing, loadingMore). The overlay was checked in Arabic / RTL.

## Deliberate exceptions

**Skeletons kept** (the first load of the page is the BrandLoader overlay; these only show for in-page refreshes
or inside a widget, where a skeleton holds the exact layout and avoids a jump):

- Category, search and shop product grids (`ProductCardSkeleton`, `SkeletonGrid`, `shop/_components/*`) — kept
  for filter / sort / search refreshes, as the brief allows for a good product-grid skeleton.
- Deals grid (`DealSkeleton`) — same, for filter changes.
- Homepage sections below the feed (`HomeCategoryCarousel`, `CategoryShowcase`, `FlashDealsSection`,
  `PacksSection`, `BrandCollectionSection`, `AboveFoldProducts`, `ProductRecommendations`) — independent
  widgets; the page's first load is held by `HomeFeed`.
- Profile tabs (`ComplaintsTab`, `FavoritesTab`, `ReviewsTab`) — tab switches inside a loaded page.
- `QuickView`, `LocalSpotlight`, `AttributeFilterPanel`, the Navbar mega-menu product preview — small previews
  whose skeleton matches the final cards.
- `PriceAnalysisLoader` in the AI price optimizer — a step-by-step progress panel (each step uses the inline
  BrandLoader glyph); kept because it shows real progress.

**Fetching components not wired to the overlay** (background widgets, they must never block a page):
countdown timers, ad strip / entry popup, review prompt popup, notification polling (`Usenotifications`),
`NotificationBell` (now shows a section loader in its dropdown), `ProfileGate`, `PickupAddressBanner`,
`Topbar`, `ShareStore`, `CardGallery`, `ProductFilterSidebar` facets, `useSubscription` (its consumers —
`PlanGate`, the Black pages — hold the overlay), the become-a-vendor landing sections (the page itself holds
the overlay until role + plans are known).

**Pending states that are not UI**: `context/CartContext.tsx` (`loadingItemId` is rendered by `CartDrawer` with
the inline loader; `cartLoading` / `favLoading` are consumed by checkout / favorites, which hold the overlay),
`app/orders/page.tsx` `pendingPrompts` (a review-prompt queue), Navbar `loadingP` (mega-menu preview skeleton).

**Leftover grep hit**: `app/dev/loader-preview/LoaderPreview.tsx` — the preview page's own label text.

## Not covered

- `app/dev/loader-preview` — dev-only page, 404 in production.
- Checkout "place order" was verified in code (inline loader, button disabled) but not submitted in the browser:
  it would create a real order in the dev database.
